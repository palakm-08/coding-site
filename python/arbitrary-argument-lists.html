Python Arbitrary Argument Lists Explained (Python Docs 4.9.4) | *args & Keyword-Only Params After It

This page explains the official Python Arbitrary Argument Lists documentation (Python Docs 4.9.4) in simple language. Sometimes you don't know ahead of time how many arguments a function will need to accept — *args lets a function scoop up any number of extra positional arguments into a single tuple.

By the end of this guide, you'll understand the write_multiple_items() example, exactly why *args almost always goes last in a parameter list, and how anything defined after it automatically becomes keyword-only — demonstrated with the concat() example straight from the docs.

What Are Arbitrary Argument Lists? (Python Docs 4.9.4 Explained)

An arbitrary argument list lets a function accept any number of positional arguments — zero, one, or a hundred — without needing to define a fixed set of parameter names for each one. The docs call this the least frequently used of the special parameter options, but it's genuinely useful whenever the exact number of inputs can't be known in advance.

From the Python docs

The least frequently used option is to specify that a function can be called with an arbitrary number of arguments. These arguments will be wrapped up in a tuple. Before the variable number of arguments, zero or more normal arguments may occur.

The write_multiple_items() Example

The docs introduce *args with a small function that writes any number of strings to a file, joined by a separator:

def write_multiple_items(file, separator, *args):
└── normal arguments zero or more, come first
└── *args collects everything else into a tuple
PythonPython docs example
def write_multiple_items(file, separator, *args):
    file.write(separator.join(args))

file and separator are ordinary required parameters. Everything else passed to the function — however many items — lands inside the tuple args, ready for separator.join(args) to stitch together.

Kiddo extra — announcing an arbitrary number of Hawkins residents

PythonKiddo example
def announce_party(mission, *members):
    print(f"Mission: {mission}")
    for member in members:
        print(f"- {member} is in")

announce_party("Find Will", "Mike", "Dustin", "Lucas")
# Mission: Find Will
# - Mike is in
# - Dustin is in
# - Lucas is in

# Works with any number of members — even just one, or none at all
announce_party("Scout the Upside Down", "Eleven")
# Mission: Scout the Upside Down
# - Eleven is in

Why *args Scoops Up Remaining Arguments

Because *args collects every positional argument that isn't already claimed by a named parameter, it's normally placed last in the parameter list — anything else placed after it would only ever receive its value by keyword, since there's no way to know where the variadic input ends.

From the Python docs

Normally, these variadic arguments will be last in the list of formal parameters, because they scoop up all remaining input arguments that are passed to the function.

Parameters After *args Are Keyword-Only

This is the detail that surprises a lot of people the first time they see it: any parameter defined after *args automatically becomes keyword-only. You don't need to add a separate * — *args itself already acts as that dividing line.

From the Python docs

Any formal parameters which occur after the *args parameter are 'keyword-only' arguments, meaning that they can only be used as keywords rather than positional arguments.

The concat() Example

The docs demonstrate this exact rule with a function that joins any number of strings using a configurable separator — sep comes after *args, so it can only ever be passed by keyword:

PythonPython docs example
def concat(*args, sep="/"):
    return sep.join(args)

concat("earth", "mars", "venus")
'earth/mars/venus'

concat("earth", "mars", "venus", sep=".")
'earth.mars.venus'

Notice that sep has a default value, so calls that don't need a custom separator can leave it out entirely — but if you do want to change it, you have no choice but to name it explicitly. concat("earth", "mars", "venus", ".") would not set the separator; it would just get swallowed into args as a fourth string.

Kiddo extra — joining a list of names with a custom separator

PythonKiddo example
def campaign_crew(*names, joiner=" and "):
    return joiner.join(names)

print(campaign_crew("Robin", "Steve", "Nancy"))
# Robin and Steve and Nancy

print(campaign_crew("Robin", "Steve", "Nancy", joiner=", "))
# Robin, Steve, Nancy
joiner must be named. Because joiner comes after *names, writing campaign_crew("Robin", "Steve", ", ") would not set the separator — ", " would just become a third name inside names, and joiner would quietly stay at its default.

Common *args Mistakes

Trying to pass a value after *args positionally

Any parameter following *args is keyword-only. Passing it positionally doesn't raise an error — it just silently gets absorbed into args instead, which can be a confusing bug to track down.

Assuming *args works with any iterable directly

*args collects positional arguments passed at call time — it doesn't automatically unpack a list or tuple you already have. To spread an existing sequence into separate arguments, use *my_list at the call site: func(*my_list).

Putting *args somewhere other than near the end

While technically only parameters after it are affected, putting *args anywhere but near the end of the signature usually signals confused design — everything meaningful after it has to be keyword-only, which is easy to forget while writing the call.

Forgetting args is a tuple, not a list

Inside the function, args is a tuple — it supports indexing and iteration just fine, but you can't .append() to it directly. Convert with list(args) first if you need to modify it.

Using *args when a fixed signature would be clearer

If a function realistically only ever takes two or three specific things, naming them explicitly is clearer than an open-ended *args. Reach for *args when the count is genuinely unknown or unbounded, not as a shortcut to skip naming parameters.

Arbitrary Argument List Interview Questions and Answers

Q1 What does *args do in a Python function definition?
It lets the function accept any number of extra positional arguments, which get collected into a single tuple named args (the name itself is just a convention — any valid identifier works after the *).
Q2 Why is *args usually placed at the end of a parameter list?
Because it scoops up every remaining positional argument passed to the function. Since there's no way to know in advance how many values it will absorb, placing normal positional parameters after it wouldn't make sense.
Q3 What happens to parameters defined after *args in the function signature?
They automatically become keyword-only — they can only be supplied by explicitly naming them in the call, exactly as if a bare * had been placed before them.
Q4 In def concat(*args, sep="/"), can you call concat("a", "b", "c", ".") to set sep to "."?
No. "." in that position is still a positional argument, so it gets absorbed into args as a fourth item rather than setting sep. You must call it as concat("a", "b", "c", sep=".") instead.
Q5 What data type does *args produce inside the function body?
A tuple. All the extra positional arguments passed to the call are collected into this tuple in the order they were given, and the function can iterate over or index into it like any other tuple.
Q6 Can a function combine normal parameters, *args, and keyword-only parameters together?
Yes — this is exactly the pattern the docs demonstrate. Normal parameters come first, *args follows to catch any extra positional values, and any parameters after that are automatically keyword-only, like sep="/" in the concat() example.
