Python Special Parameters Explained (Python Docs 4.9.3) | Positional-Only (/), Keyword-Only (*) & Combined Signatures

📖 Based on Python 3 official docs §4.9.3 — explained like a friend, with extra examples added
Python Functions Intermediate Official Docs Updated July 2026

This page explains the official Python Special Parameters documentation (Python Docs 4.9.3) in simple language. By default, arguments can be passed either by position or by keyword — but sometimes you want to restrict that, so callers can't rely on a parameter name that might change, or can't skip naming something that really needs to be explicit.

By the end of this guide, you'll understand exactly what / and * do in a function signature, walk through all four example functions from the docs, and see the one genuinely tricky collision between a positional parameter name and **kwargs that / was specifically designed to solve.

What Are Special Parameters? (Python Docs 4.9.3 Explained)

By default, every argument in Python can be passed either by position or by keyword — whichever the caller prefers. Special parameters let a function's author restrict that, so a developer only has to look at the function definition to know exactly how each argument is meant to be passed.

/ marks positional-onlyParameters before it can never be passed by keyword
* marks keyword-onlyParameters after it can never be passed by position
Both are optionalA signature with neither behaves exactly as before — position or keyword, freely
Improves readabilityThe signature itself documents how each argument must be called

Reading a Function Signature With / and *

A function signature using both markers looks like this. Everything before / is positional-only, everything between / and * can be either, and everything after * is keyword-only:

def f(pos1, pos2, / , pos_or_kwd, * , kwd1, kwd2):
└── Positional only must be passed by position
└── Positional or keyword either way works
└── Keyword only must be named explicitly
From the Python docs

Where / and * are optional. If used, these symbols indicate the kind of parameter by how the arguments may be passed to the function: positional-only, positional-or-keyword, and keyword-only. Keyword parameters are also referred to as named parameters.

Positional-or-Keyword Arguments — The Default

If a function definition has no / and no *, every argument may be passed either by position or by keyword — this is the behavior you've been using all along in every function so far.

From the Python docs

If / and * are not present in the function definition, arguments may be passed to a function by position or by keyword.

Positional-Only Parameters

Parameters placed before a / in the signature are positional-only — their order matters, and they can never be passed by keyword, no matter what name they have.

From the Python docs

It is possible to mark certain parameters as positional-only. If positional-only, the parameters' order matters, and the parameters cannot be passed by keyword. Positional-only parameters are placed before a / (forward-slash), which is used to logically separate the positional-only parameters from the rest. If there is no / in the function definition, there are no positional-only parameters. Parameters following the / may be positional-or-keyword or keyword-only.

Keyword-Only Arguments

To force parameters to be passed by keyword, place a * in the parameter list just before the first keyword-only parameter. Everything after that * must be named explicitly in any call.

From the Python docs

To mark parameters as keyword-only, indicating the parameters must be passed by keyword argument, place an * in the arguments list just before the first keyword-only parameter.

Kiddo extra — forcing a substitution reason to be named

PythonKiddo example
def make_substitution(player_off, player_on, *, reason):
    print(f"{player_off} off, {player_on} on — {reason}")

# player_off and player_on can be positional or keyword — no * before them
make_substitution("Haaland", "Foden", reason="tactical")
# Haaland off, Foden on — tactical

# But reason MUST be named — it comes after the *
make_substitution("Haaland", "Foden", "tactical")
# TypeError: make_substitution() takes 2 positional arguments but 3 were given
Forcing reason to be keyword-only here isn't arbitrary — make_substitution("Haaland", "Foden", "tactical") reads ambiguously (which string is which?), while reason="tactical" makes the call self-explanatory at a glance. That's the whole motivation for *, seen in a one-line example before the docs' own four functions make the same point more formally.

The Four Example Functions

The docs walk through four small functions, each demonstrating one calling convention at a time:

PythonPython docs example
def standard_arg(arg):
    print(arg)

def pos_only_arg(arg, /):
    print(arg)

def kwd_only_arg(*, arg):
    print(arg)

def combined_example(pos_only, /, standard, *, kwd_only):
    print(pos_only, standard, kwd_only)

combined_example() — All Three Conventions Together

combined_example(pos_only, /, standard, *, kwd_only) uses every rule at once: pos_only must be positional, standard can be either, and kwd_only must be named.

combined_example(1, 2, 3)

combined_example(1, 2, kwd_only=3)
1 2 3

combined_example(1, standard=2, kwd_only=3)

The name / **kwds Collision Problem

Here's the scenario / was specifically built to solve. If a function has a positional parameter called name and also accepts **kwds, there's no way to pass 'name' as a key inside **kwds — Python always binds it to the parameter first, causing a conflict.

PythonPython docs example
def foo(name, **kwds):
    return 'name' in kwds

foo(1, **{'name': 2})
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
TypeError: foo() got multiple values for argument 'name'

There is no possible call that makes foo return True as written — the keyword 'name' always binds to the first parameter. But marking name as positional-only frees up 'name' as a key inside **kwds:

PythonPython docs example
def foo(name, /, **kwds):
    return 'name' in kwds

foo(1, **{'name': 2})
True
In other words, the names of positional-only parameters can be used inside **kwds without ambiguity — since name can never be matched by keyword, the string 'name' is free to be treated as just another entry in the keyword dictionary.

Kiddo extra — the same fix on a player lookup function

PythonKiddo example
# Without / — colliding with a 'club' key in extra_info
def show_player(club, **extra_info):
    return club, extra_info

# This fails — 'club' collides with the positional parameter
# show_player("Real Madrid", **{"club": "on loan"})

# With / — club is now positional-only, so 'club' is free in kwargs
def show_player(club, /, **extra_info):
    return club, extra_info

print(show_player("Real Madrid", **{"club": "on loan"}))
# ('Real Madrid', {'club': 'on loan'})

Recap — Which One to Use, and When

The use case decides which parameters to make positional-only, keyword-only, or leave flexible:

Use positional-only when
  • The parameter name has no real meaning to the caller
  • You want to enforce a strict argument order
  • You need to accept positional parameters alongside arbitrary keywords, avoiding name collisions
  • You're building a public API and don't want a future rename to break callers
Use keyword-only when
  • The name carries real meaning and makes the call clearer
  • You want to prevent callers from depending on argument position
  • The function has several optional flags that read better named
  • You want to be free to reorder parameters later without breaking callers
From the Python docs

For an API, use positional-only to prevent breaking API changes if the parameter's name is modified in the future.

Common Special Parameter Mistakes

Trying to pass a positional-only parameter by keyword

pos_only_arg(arg=1) fails with got some positional-only arguments passed as keyword arguments, even though the parameter is literally named arg. The / makes the name irrelevant to callers.

Trying to pass a keyword-only argument by position

kwd_only_arg(3) fails with takes 0 positional arguments but 1 was given. Everything after * must always be named in the call.

Putting * before / in a signature

/ must come before * if both appear — positional-only parameters, then flexible ones, then keyword-only ones, in that left-to-right order. Reversing them is a SyntaxError.

Not realizing why a **kwargs collision happens

def foo(name, **kwds) called as foo(1, **{'name': 2}) fails, because Python always binds a keyword argument to a matching parameter name first — regardless of whether it came from **kwds unpacking. Making name positional-only removes the collision.

Overusing keyword-only or positional-only everywhere

These markers are useful tools for API design, but forcing them onto every small internal helper function adds friction without much benefit. Reach for them deliberately, not by default.

Special Parameters Interview Questions and Answers

Q1 What do the / and * symbols mean in a Python function signature?
A / marks every parameter before it as positional-only — it cannot be passed by keyword. A * marks every parameter after it as keyword-only — it cannot be passed by position. Both are optional and can appear together in the same signature.
Q2 What error do you get if you call a positional-only parameter by keyword?
A TypeError saying the function "got some positional-only arguments passed as keyword arguments," naming the offending parameter — even though the parameter genuinely has that name in the definition.
Q3 Why would a library author choose positional-only parameters?
Mainly to protect an API from future breakage — if the parameter's internal name changes later, callers who never named it explicitly are unaffected. It's also useful to enforce a specific argument order, or to free up a name for use inside **kwargs.
Q4 Explain the foo(name, **kwds) collision problem.
If name is an ordinary positional-or-keyword parameter, any keyword argument named name in a call always binds to that parameter first — even one unpacked from **{'name': 2} — causing a TypeError for "multiple values." Marking name positional-only with / resolves this, since it can never be matched by keyword, leaving 'name' free to land inside **kwds.
Q5 In def f(pos_only, /, standard, *, kwd_only), which calling styles are valid for each parameter?
pos_only must be passed positionally only. standard can be passed either positionally or by keyword. kwd_only must always be passed by keyword.
Q6 Can a function signature use / without *, or * without /?
Yes — both are independent and optional. A signature can have positional-only parameters with no keyword-only ones, keyword-only parameters with no positional-only ones, both together, or neither.
